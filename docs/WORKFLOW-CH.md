# SWFT 算子开发 Harness —— Workflow 汇报材料

> 背景:本工程把"为上游模型开发并极致调优 SWFT DSL 算子、编译成 .so"这件事,拆成可分步执行的流水线。约束很硬:**气隙工作机 + 内源量化弱模型(可用上下文 ~400k)**。
>
> 本文档对比两版 workflow:**旧版(已执行过)** 与 **新版(重构后,尚未执行)**。新版是对旧版的改进,逐条解掉旧版暴露的困难。

---

## 一、旧 Workflow(已执行版本)

### 核心思路

把整模型计算图**切成子图**,再把子图按相似性组成 **family bundle**,每个 bundle 开一个 agent 会话,让 agent **依据规格、参考资料,从头合成该子图的 SWFT DSL**,逐子图与 torch golden 对拍。

### 流程图

```
┌─────────────────────────────────────────────────────────────────┐
│                      旧 Workflow(七阶段线性)                      │
└─────────────────────────────────────────────────────────────────┘

  上游模型 (torch class + model_config + weights.pth)
        │
        ▼
  ┌──────────────┐
  │ 01 torch导出  │  → model_ir + node_manifest + weight_map + torch_runner
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │ 02 切图       │  → partition_plan.json  (子图 ≈ 一层encoder/embedding/mask)
  └──────┬───────┘
         ▼
  ┌───────────────┐
  │ 03 torch golden│ → 逐 partition 边界的 input/output golden bins
  └──────┬────────┘
         ▼
  ┌──────────────┐
  │ 04 DSL骨架    │  → 趟平 compile/run/file-IO 的最小骨架 (GM→UB→GM)  ★每模型必经
  └──────┬───────┘
         ▼
  ┌──────────────────────────────────────────────────────────┐
  │ 05 DSL实现 (family bundle 分会话)                          │
  │                                                            │
  │   主 agent ──组 family bundle──┐                           │
  │      ▼                         ▼                           │
  │  work agent(一个bundle)    judge agent(双包隔离)         │
  │   按 subgraph_order 串行:                                  │
  │   【依据规格 + 参考资料, 从零合成子图DSL】← 弱模型最弱的模式  │
  │   compile → run → 与 golden 对拍 → 过了才下一个子图          │
  └──────┬─────────────────────────────────────────────────────┘
         ▼
  ┌──────────────┐
  │ 06 整图集成    │  → 拼成整模型 DSL + 整图对拍
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │ 07 时延优化    │  → 优化到目标时延, 保正确性
  └──────────────┘
```

### 旧 Workflow 暴露的困难

| # | 困难 | 根因 |
|---|---|---|
| **1** | **弱模型直接罢工** | 让它"理解规格 → 合成 DSL"正中它最弱的模式;它判断"太复杂、实现麻烦"就不干。子图拆分缓解了一部分,但 05 里每个子图仍是"从零创作一整层"。 |
| **2** | **最大杠杆没用上** | 范本库(44 个已验证算子实现)只被当作**整文件只读参考**(`similar_model_dsl`),而不是"针对当前算子检索最像的那一段来抄"。"检索+最小改写"这个弱模型最擅长的动作几乎没用。 |
| **3** | **经验断链** | 04 阶段专门趟平编译/IO 路径,但 05 实现 DSL 时**仍在 input 路径上犯同样的错**——上一步的有效经验没能精确传到下一步。经验压在静态散文文档里,不随运行流动。 |
| **4** | **粒度断层** | 子图("一整层 encoder"=多算子串联)与范本("单个融合算子")之间差了一个层级,弱模型的活始终落在"实现一整层"的过大粒度上。 |
| **5** | **上下文臃肿** | agent 按 AGENT_TASK.md 读完一堆规格+参考资料,还没动手就已占用大量 token,逼近智力下降阈值。 |
| **6** | **07 调优过于乐观** | 把极致调优当成"再查个范本"就行,没有可机械执行的调优协议。 |

## 二、新 Workflow(重构版,尚未执行)

### 核心转变(一句话)

> 把流水线的原子动作,从"**为算子写 DSL**"换成"**取最像的已验证范本 → 最小改写到对拍通过**"。

并补上关键的**算子中间层**:模型 → 子图(~16) → **算子(5–10/子图,新增)** → 范本。弱模型的活永远落在最底层"把这个范本改到这组 shape、用这份 golden 对拍通过",**从不面对"实现一整层"**。

### 流程图


### 新 Workflow 如何逐条解掉旧困难

| 旧困难 | 新 Workflow 的解法 |
|---|---|
| **1 罢工** | 原子动作换成"改一个范本到对拍",弱模型最擅长的模仿改写,小到不会判定"太复杂"。 |
| **2 杠杆没用上** | 范本索引子系统:按算子签名检索最像的 1–2 段范本正文注入,"检索+最小改写"成为主线动作。 |
| **3 经验断链** | **问题消失而非修复**:每个范本本身自带跑通的"造数+编译+对拍"完整链路,IO 经验是范本的副产品,不需要从 04 往 05 传。 |
| **4 粒度断层** | 新增**算子中间层**,补上子图与范本之间缺的那一级。 |
| **5 上下文臃肿** | 每个 worker 只看一个算子的极小上下文(IR切片+一段范本+一份golden+几个API签名);driver 确定性编排避免母会话收集 N 个子结果。 |
| **6 调优乐观** | 07 拆成 07A(可机械执行的有界爬山+move catalog)和 07B(专家档,诚实升级人/强模型),不赌全自动。 |

### 额外新增的杠杆(旧版没有)

- **API 真值源** `api_reference.json`:从编译器前端源码自动枚举 API 签名,根治"幻觉 API/用错签名"。
- **两层经验回流**:run-local(对拍即入库,重复 encoder 层近零改写)+ global(人工确认闸,跨模型复利)。
- **分层故障检索 L1/L2/L3**:出错时定向 grep 报错相关的源码,而非通读。
