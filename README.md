# SWFT DSL Harness

This repository contains a file-driven workflow for end-to-end SWFT DSL development.
It follows route B: the trusted PyTorch model is the single semantic source.
The pipeline exports and validates a machine-readable IR, partitions that IR,
and captures per-partition golden data directly from PyTorch. Stage 01 uses
`model_config.json` to identify the target class, constructor kwargs, and entry
method.

## Pipeline

Default stages:

1. `01_torch_export`: export and validate `model_ir.json`, `node_manifest.json`,
   `weight_map.json`, `input_spec.json`, and `torch_runner.py`.
2. `02_partition`: split the validated IR into SWFT-friendly partitions.
3. `03_torch_golden`: capture per-partition input and golden output bins from PyTorch using the configured dtype policy.
4. `04_dsl_skeleton`: prove the SWFT compile/run/file I/O loop works.
5. `05_dsl_partitions`: a main agent coordinates multiple subagents to implement partitions.
6. `06_dsl_integrate`: merge accepted partition implementations into a full DSL.
7. `07_perf`: optimize latency without breaking correctness.

Agents do not talk to each other directly. The orchestrator passes only validated
files to the next stage.

## Quick Start

Initialize a workspace:

```bash
python3 scripts/init_pipeline.py --workspace work
```

`init_pipeline.py` creates `work/input_paths.json`. By default, user-provided
inputs are expected here:

```text
work/shared/model/model.py
work/shared/model/weights.pth
work/shared/model/model_config.json
work/shared/similar_dsl/similar_model_dsl.py
```

If your filenames differ, do not edit harness code. Put the files somewhere
under the workspace and update `work/input_paths.json`, for example:

```json
{
  "torch_model_source": "shared/model/my_model_impl.py",
  "torch_model_config": "shared/model/model_config.json",
  "torch_weights": "shared/model/checkpoint_epoch_20.pth",
  "similar_model_dsl": "shared/similar_dsl/corr_model_dsl_v3.py"
}
```

Paths may be workspace-relative or absolute. Stage packages render the resolved
paths into `INPUT_MANIFEST.json` and `JUDGE_INPUT_MANIFEST.json`.

`model_config.json` is created by `init_pipeline.py`. Fill `model_class`,
`model_kwargs`, and `entry_method` before packaging stage `01_torch_export`.
The weight file path comes from the `torch_weights` label in `input_paths.json`;
do not hard-code it in `model_config.json`.
`input_spec.json` is generated by stage `01_torch_export`.

Check configured inputs before packaging:

```bash
python3 scripts/check_inputs.py --workspace work --stage 01_torch_export
```

Package the current stage:

```bash
python3 scripts/package_stage.py --workspace work
```

Give the generated directory to the current stage agent:

```text
work/stages/01_torch_export/agent_package/
```

After the agent writes files under the stage output directory, run:

```bash
python3 scripts/validate_stage.py --workspace work --stage 01_torch_export
python3 scripts/validate_judge.py --workspace work --stage 01_torch_export
python3 scripts/advance_stage.py --workspace work
```

Repeat: package both worker and judge tasks -> manually start a worker session with the worker package -> worker work -> mechanical validation -> manually start a judge session with the judge package -> judge validation -> advance.

## How Task Packages Are Built

`package_stage.py` does not use a hard-coded prompt per stage.
It reads:

```text
work/pipeline_state.json
configs/pipeline.default.json
```

Then it combines a generic template, the current stage configuration, and the
current workspace state to build the task package.

The most important stage fields are:

```text
id                 stage identifier
agent_role         agent role for this stage
objective          what this stage should do
input_refs         inputs this stage may read
allowed_edits      paths this stage may modify
required_outputs   outputs this stage must produce
validation_commands extra machine checks
procedure           stage-specific steps rendered into AGENT_TASK.md
quality_checks      worker self-checks before handoff
```

Each task package always includes:

```text
agent_package/AGENT_TASK.md        worker task description
agent_package/INPUT_MANIFEST.json  worker input manifest
agent_package/OUTPUT_CONTRACT.json required worker output contract
agent_package/VALIDATION.md        worker mechanical validation instructions
judge_package/JUDGE_TASK.md        judge task description
judge_package/JUDGE_INPUT_MANIFEST.json judge input manifest
judge_package/JUDGE_GUIDE.md       general judge guide
```

The stage configuration in `configs/pipeline.default.json` is what drives behavior.
`AGENT_TASK.md` is intended to be complete enough that the worker agent does not
need additional hand-written prompt text for that stage.
`AGENT_TASK.md` does not mention the judge or pipeline advancement. The worker
stops after the current stage deliverables and mechanical validation. `judge_checklist`
is only rendered into the judge package so the worker cannot optimize directly
against the judge checks.

## Validation and Judge

Run:

```bash
python3 scripts/validate_stage.py --workspace work --stage <stage_id>
```

The mechanical validator checks:

1. Whether all declared `required_outputs` exist.
2. Whether all configured `validation_commands` return success.

If validation fails, it prints the missing files or failing commands and writes:

```text
work/stages/<stage_id>/validation/VALIDATION_REPORT.json
```

`package_stage.py` already created the independent judge package. After
mechanical validation passes, give this directory to a fresh judge agent that did
not inherit the worker agent's context:

```text
work/stages/<stage_id>/judge_package/
```

The judge writes:

```text
work/stages/<stage_id>/judge/JUDGE_REPORT.json
```

Then run:

```bash
python3 scripts/validate_judge.py --workspace work --stage <stage_id>
```

`advance_stage.py` requires both mechanical validation and judge validation.

Do not run `advance_stage.py` after a failed validation or failed judge.
Instead:

1. Open `VALIDATION_REPORT.json`.
2. If judge failed, also open `JUDGE_REPORT.json`.
3. Give the failure report to the current stage agent.
4. Let that agent fix only the files allowed for that stage.
5. Re-run mechanical validation and judge validation.
6. Advance only after both pass.

If the current agent cannot fix the issue, you may re-run `package_stage.py`
and hand the new package plus the failure report to another agent.

## Parallel DSL Subgraphs

Stage `05_dsl_partitions` is coordinated by a main agent. The main agent first
generates one isolated task package per partition:

```bash
python3 scripts/package_dsl_subagents.py --workspace work --clean
```

To package only partitions that are currently ready for independent implementation:

```bash
python3 scripts/package_dsl_subagents.py --workspace work --clean --ready-only
```

The generated packages are placed under:

```text
work/stages/05_dsl_partitions/subagent_packages/<partition_id>/
```

The script also writes:

```text
work/stages/05_dsl_partitions/output/subagent_task_manifest.json
```

That manifest lists:

```text
ready_partitions    tasks that can be given to separate manual agent sessions
blocked_partitions  tasks blocked by implementation_deps or can_implement_independently=false
package_path        package directory for each subagent task
```

Dependency fields have different meanings:

```text
semantic_deps        graph dataflow deps; usually not a development blocker when torch-captured partition inputs exist
implementation_deps layout, fusion, or shared-code deps; wait or group these with their dependency/fusion group
```

Each subagent reads only its own `partition.json`, `INPUT_MANIFEST.json`, and
`OUTPUT_CONTRACT.json`, and writes only to its own output directory:

```text
work/stages/05_dsl_partitions/output/partitions/<partition_id>/
```

The recommended launch mode is manual: open one fresh agent session for each
`package_path`, give that session the package path, and ask it to follow
`AGENT_TASK.md`. Subagents should not edit shared `target_dsl/` files or any
other partition output directory.

The main agent later collects the validated partition implementations and writes:

```text
work/stages/05_dsl_partitions/output/partition_impl_manifest.json
work/stages/05_dsl_partitions/output/dsl_progress.json
work/stages/05_dsl_partitions/output/partition_correctness_report.json
```

This keeps different subagents isolated while they work on different subgraphs.

## Contract

Each stage owns only its own directory:

```text
work/stages/<stage_id>/
  agent_package/
  judge_package/
  output/
  logs/
  validation/
  judge/
```

Agents should modify only files allowed by `AGENT_TASK.md`.

Route B means the `01_torch_export` stage must pass before later stages may
consume `model_ir.json`, `node_manifest.json`, `weight_map.json`,
`input_spec.json`, and `torch_runner.py`.

## Important

This harness does not call an LLM itself and does not automatically start agents.
It is only the workflow controller:
it packages tasks, tracks state, validates outputs, and advances stages.
